# MassAwareArm Codebase Guide (integration branch)

This guide explains how the codebase works **as of the `integration` branch**, which adds
a major new subsystem on top of `main`: a trajectory-tracking pipeline
(`massaware/controllers/` + `scripts/mission_tracking.py` and friends) and a fourth
estimator (`estimators/inverse_dynamics.py`). If you last read the code on `main`,
sections 4–6 are the new material.

For per-method math derivations see [PID_ERROR.md](PID_ERROR.md), [LYAPUNOV.md](LYAPUNOV.md),
[MOMENTUM_OBSERVER.md](MOMENTUM_OBSERVER.md), and [ARCHITECTURE.md](ARCHITECTURE.md).

---

## 1. The big picture

A simulated UR5e in MuJoCo picks a cube, infers the cube's mass **without any force
sensor**, classifies it light/heavy against a threshold, and drops it in the matching
bin. The scientific payload of the project is the side-by-side comparison of mass
estimators that all consume the same per-tick observation stream.

There are now **two parallel mission pipelines** in the repo:

| | Legacy FSM pipeline | New tracking pipeline |
|---|---|---|
| Entry script | `scripts/mission.py`, `scripts/verify_estimators.py` | `scripts/mission_tracking.py`, `scripts/compare_tracking_controllers.py` |
| Motion representation | Discrete `Step`s (move-to-pose, settle, hold) inside an FSM; setpoint jumps | Smooth LSPB joint trajectories with continuous `q(t), q̇(t), q̈(t)` references |
| Controller | `massaware/controller.py` `PIDController` (setpoint PID + gravity comp) | `massaware/controllers/` `TrackingPIDController` or `InverseDynamicsTrackingController` (track full references) |
| Weighing style | Dedicated **WEIGH state**: move to weigh pose, settle (pause), hold, sample | A **trajectory segment** flagged `collect_mass_samples`; sampling can happen during the lift motion itself — no pause required |
| Payload physics | Cube physically grasped by the 2f85 gripper (contact forces) | Cube **kinematically pinned** to the EE + payload weight applied as a pure force (`TrackingAttachment`) |
| Estimators | pid_error, lyapunov, momentum_observer (inverse_dynamics also usable via `mission_inverse_dynamics_estimator.py`) | all four |

Both pipelines share the same low-level layers (`mujoco_env`, `robot`, `estimators/`,
`classify`, `config`) and the same `EstimatorObs` per-tick observation contract, which is
what lets one estimator implementation serve both.

## 3. Core shared layers

### 3.1 `mujoco_env.py` — the only file that touches raw MuJoCo state

`MujocoEnv` loads `assets/scene.xml` and exposes exactly what the rest of the code needs:

- `get_arm_qpos() / get_arm_qvel()` — 6-vector arm state (address-mapped, robust to DOF ordering).
- `set_arm_ctrl(tau)` — writes arm torques, **returns the ctrlrange-clipped command**.
- `qfrc_bias` (property) — MuJoCo's bias force `C(q,q̇)q̇ + g(q)` for the 6 arm DOFs.
  Note: this does *not* include joint armature effects on momentum, passive spring/damper
  forces, or constraint (contact) forces.
- `gravity_torque(q)` — pure `g(q)` evaluated in a scratch `MjData` with `q̇=0`
  (used by the tracking controllers to separate gravity from Coriolis).
- `mass_matrix()` — dense 6×6 joint-space inertia `M(q)` (includes armature).
- `actuator_force` — per-joint applied torque read from the `actuatorfrc` sensors
  declared in `scene.xml` (this is the "measured torque" channel `tau_meas`).
- `ee_pose()` — world position + rotation of the `gripper_pinch` site.
- `set_body_mass(name, m)` — runtime cube re-massing between trials (scales inertia,
  refreshes `mj_setConst`), so a sweep never reloads the XML.

### 3.2 `robot.py` — kinematics

`Robot.fk(q)`, `Robot.jacobian_ee(q)` (3×6 linear Jacobian of the EE site, evaluated by
temporarily setting `qpos` then restoring), and `Robot.ik(xyz, q_seed)` — damped
least-squares, position-only IK. The tracking pipeline has its own *analytical* full-pose
IK (§5.4) and uses this one only for the `main` profile.

### 3.3 `estimators/` — the estimator contract (read this first)

`base.py` defines the whole interface:

- **`EstimatorObs`** — the per-tick observation every estimator receives:
  `t, q, q_dot, tau_cmd, tau_meas, qfrc_bias, jacobian_ee (3×6), q_ref, ee_xyz, M (6×6)`.
  Both pipelines construct this identically (`tick_loop._build_obs` /
  `mission_tracking.build_obs`), which is the seam that lets estimators be pipeline-agnostic.
- **`Estimator`** ABC:
  - `reset() / update(obs) / estimate() -> EstimateResult` — the measurement lifecycle.
  - `gravity_comp_mask(n)` — per-joint multiplier on the gravity feedforward while the
    estimator is active (pid_error zeroes its measurement joint; everyone else returns ones).
  - `controller_overrides()` — gain overrides requested while measuring (lyapunov softens
    kp/kd and zeroes ki; pid_error softens just the measurement joint; the other two return `{}`).
  - `requires_calibration` + `start_/update_/finish_/load_calibration` — the empty-arm
    baseline protocol (see §7).
- **`registry.py`** — `register(name, cls)` at module bottom of each estimator file +
  `build(name, cfg)` at startup. Adding an estimator = one new file + one `register()` call
  + a YAML block + an import in the entry script.

### 3.4 The four estimators

| name | needs calibration | reads | physics in one line |
|---|---|---|---|
| `pid_error` | yes | `tau_cmd[joint 2]` | Disable gravity comp at the elbow; the controller's steady torque minus the empty baseline equals `m·g·(moment arm)`, with the moment arm read live from `J_z` |
| `lyapunov` | yes | `q`, `ee_z` | Soften kp (×0.1), zero ki; arm sags under payload; energy balance gives `m = 2ΔE_spring/(gΔh)` |
| `momentum_observer` | yes | `tau_cmd, q̇, M, qfrc_bias, J_z` | Generalized-momentum disturbance observer; residual `r → τ_ext`; project `r − r_empty` onto `−g·J_z` (see [MOMENTUM_OBSERVER.md](MOMENTUM_OBSERVER.md) and [MOMENTUM_PAUSE_FREE_PLAN.md](MOMENTUM_PAUSE_FREE_PLAN.md)) |
| `inverse_dynamics` | **no** | `tau_meas` (or `tau_cmd`), `qfrc_bias`, `J` | Per-tick residual `τ − qfrc_bias` regressed against the per-kg gravity torque `Jᵀ[0,0,−g]`; gates out samples with high `‖q̇‖` or tracking error, so it works during gentle motion **without a pause and without calibration** |

The `inverse_dynamics` estimator is the model for "weigh while moving": every tick it
forms a one-parameter least-squares problem (mass) from the residual torque, rejects
dynamic samples by gating (`max_q_dot_norm=0.35`, `max_q_error_norm=0.25`), and at
`estimate()` solves `m̂ = −Σ⟨A_k, res_k⟩ / Σ‖A_k‖²` with `A_k = J_kᵀ[0,0,−g]` varying
per sample. No empty-arm baseline is needed because `qfrc_bias` already accounts for the
arm+gripper model exactly in sim.

### 3.5 `classify.py`, `perception/`, `config.py`

One-liner threshold classifier; ground-truth perception that reads the cube body pose
straight from MuJoCo (CV backend is a future stub); YAML loader that converts the pose
arrays from degrees to radians at load time (`home_qpos`/`weigh_qpos` are written in
degrees in `default.yaml` — don't pass radians there).

## 4. Legacy FSM pipeline (`mission.py`)

`planner.py` implements a step-sequenced FSM driven one physics tick at a time by
`tick_loop.TickLoop` — the **single owner of `mj_step`**:

1. `fsm.tick()` lets the active state advance/choose the next state and set
   `ctx.arm_target`, `ctx.gripper_cmd`, `ctx.gravity_comp_mask`, `ctx.estimator_sink`.
2. The legacy `PIDController.compute()` produces feedback torque; the tick loop adds
   `qfrc_bias * ctx.gravity_comp_mask` **outside** the controller so a per-joint mask can
   selectively disable gravity comp (pid_error's trick).
3. `mj_step`.
4. If a state installed an `estimator_sink` (WEIGH → `estimator.update`,
   INIT calibration → `estimator.update_calibration`), the loop builds an `EstimatorObs`
   and feeds it.

State flow: `INIT` (load or produce calibration → §7) → `SEARCH` (perception) → `GRASP`
(approach/descend/close/lift via Cartesian steps + IK) → `WEIGH` → `CLASSIFY` → `PLACE` →
`HOME`. `WEIGH` is the "pausing" phase: move to `weigh_qpos`, **apply the estimator's mask
and gain overrides only after arriving** (`_EnterEstimatorModeStep`, so the move happens at
full stiffness), settle, then hold `weigh.hold_seconds` while sampling, then `estimate()`.

`verify_estimators.py` re-implements the tick loop inline (`_drive`) and sweeps
(estimator × mass) pairs through this FSM, reusing one `MujocoEnv` across trials; results
go to stdout and `results/sweep_*.csv` (plot with `scripts/plot_results.py`).

## 5. NEW: the tracking pipeline (`massaware/controllers/` + `mission_tracking.py`)

This is the teammate's major addition. Instead of jumping setpoints between FSM states,
the mission is two smooth LSPB joint-space trajectories, tracked by a controller that
consumes full `(q, q̇, q̈)` references. Weighing happens **inside the trajectory**, in
whatever segments are flagged for sampling — no settle/pause state exists at all.

### 5.1 `trajectory.py` — LSPB segments with per-segment semantics

`JointSegmentTrajectory` is a list of `TrajectorySegment`s, each an LSPB
(trapezoidal-velocity) interpolation `start → goal` over `duration` with `blend_time`
(default 25 % of the segment). `sample(elapsed)` returns a `TrajectorySample`:
`(stage, q, q_dot, q_ddot, gripper_closed, collect_mass_samples, compensate_payload, done)`.
The three boolean flags are how the trajectory *declares policy* per segment:

- `PickWeighTrajectory`: `move_to_grasp` → `grasp` (hold, gripper closes) →
  `lift_to_weigh` (optionally `collect_mass_samples=True` via `collect_lift_samples`) →
  `weigh_hold` (always `collect_mass_samples=True`; note this is a *hold segment* —
  reference constant at `q_weigh` — not a separate FSM pause).
- `ReleaseTrajectory`: `move_to_release_approach` → `move_to_release` (both with
  `compensate_payload=True`, i.e. the controller now feeds forward the **estimated** mass)
  → `release` (gripper opens).

Payload-compensation timing convention (also in `controllers/README.md`): no payload
feedforward before/during weighing (it would cancel the very signal being measured);
estimated-mass feedforward during the release motion; none after release.

### 5.2 The two tracking controllers (`base.py`, `pid_tracking.py`, `inverse_dynamics_tracking.py`)

Shared base handles gains, overrides (`apply_overrides`/`clear_overrides`, honoring
`allow_overrides`), tracking errors, gravity mask, and payload compensation
`τ_p = J(q)ᵀ[0,0,m̂g]`.

- `TrackingPIDController`: `u = Kp e + Ki∫e + Kd ė + g(q)·mask + τ_p`.
- `InverseDynamicsTrackingController` (computed torque):
  `q̈_cmd = q̈_d + Kd ė + Kp e`, then `u = M(q) q̈_cmd + (Coriolis + g·mask) + τ_p`.
  Coriolis is recovered as `qfrc_bias − gravity_torque(q)` so the mask applies to gravity only.

Both controllers **write the torque to the sim themselves** (`env.set_arm_ctrl`) and
return a rich `ControlOutput` (raw vs clipped command, feedback/feedforward/payload
splits) used by the plotting/sweep scripts. Gains come from `profiles.py`
(`tracking` profile = hand-tuned arrays; `main` profile = gains from `default.yaml`).

### 5.3 `attachment.py` — the payload model (important difference!)

In this pipeline the cube is **not physically grasped**. While `gripper_closed` is true,
`TrackingAttachment` kinematically pins the cube's free joint to the EE each tick
(collision disabled) and applies the payload weight `F = [0,0,−mg]` at the EE site via
`mj_applyFT`. Consequences worth knowing:

- The external disturbance on the arm is *exactly* `JᵀF` — pure gravity, even during
  motion. The payload's **inertial** reaction (`−m·a_ee`) is *not* simulated.
  Estimators therefore look slightly better here than in the contact-based FSM pipeline,
  and motion-phase weighing is "easier" than it would be physically.
- `step_reference()` zeroes `qfrc_applied` and calls `mj_forward` before each control
  step, then reapplies the attachment force — order matters if you modify it.

### 5.4 `ik.py` — analytical UR5e IK

Full-pose analytical IK (all 8 branch solutions, joint-limit filtered, candidates scored
by an FK error metric in MuJoCo, nearest-to-seed selection). Used by the `tracking`
profile so grasp/weigh/release joint targets are consistent and repeatable; the `main`
profile falls back to the numerical position-only `Robot.ik`.

### 5.5 `mission_tracking.py` — the runner

Flow of `run_tracking_mission()` per tick:

1. `sample = trajectory.sample(t)`; on a stage change, apply/clear the estimator's
   controller overrides depending on `sample.collect_mass_samples`.
2. Choose the gravity mask: the estimator's mask during collection segments, ones otherwise.
3. `step_reference(...)`: attachment update → `controller.command(reference, …)` → gripper → `mj_step`.
4. If `sample.collect_mass_samples`: `estimator.update(build_obs(...))` — with
   `tau_cmd = output.tau_cmd` (the **clipped** command; note the legacy tick loop passes
   the unclipped one — harmless at the weigh pose but a known inconsistency).
5. When the pick-weigh trajectory reports `done`: `estimator.estimate()` → classify →
   IK for the chosen bin → switch to the release trajectory (estimated-mass payload comp on).

If the estimator `requires_calibration`, `run_calibration()` first drives the arm to the
weigh pose, applies mask + overrides, holds `--calibration-time` seconds while feeding
`update_calibration`, then `finish_calibration()`/`load_calibration()` **in memory only**
(the tracking pipeline does not read/write `configs/calibration.yaml`); the env is then
reset before the mission proper.

## 6. How to run things

```bash
# Environment (Python 3.11)
.venv\Scripts\Activate.ps1            # Windows
pip install -r requirements.txt

# Smoke-check the scene
python -m mujoco.viewer --mjcf=software/assets/scene.xml

# --- Legacy FSM pipeline ---
python software/scripts/mission.py --estimator momentum_observer --mass 0.5 --viewer
python software/scripts/mission_inverse_dynamics_estimator.py --mass 0.5   # same FSM, ID estimator
python software/scripts/verify_estimators.py --clear-cache                 # sweep -> results/*.csv
python software/scripts/plot_results.py results/sweep_YYYYMMDD_HHMMSS.csv  # 2x2 dashboard

# --- Tracking pipeline ---
python software/scripts/mission_tracking.py --viewer \
    --controller inverse_dynamics --estimator inverse_dynamics --mass 0.5 --profile tracking
python software/scripts/compare_tracking_controllers.py --profile tracking --masses 0.5
python software/scripts/plot_tracking_controller_errors.py --payload-comp-mode oracle \
    --disable-controller-overrides          # joint/EE/torque tracking plots
python software/scripts/sweep_tracking_payload_limits.py --payload-comp-mode oracle
    # pass/fail: joint peak error <= 2 deg, |tau_raw|/limit <= 0.95

# --- Tests ---
python -m pytest software/tests -q       # 75 tests, ~7 s
```

Useful `mission_tracking.py` knobs: `--move-to-grasp-time`, `--lift-to-weigh-time`,
`--weigh-time` (override the hold duration), `--calibration-time`,
`--disable-controller-overrides` (ignore estimator gain requests — used for clean
controller comparisons), `--profile main|tracking`.

NOTE: `verify_estimators.py` currently has its sweep grid locally edited to a single
1 kg trial (`M_MIN, M_MAX, N_MASSES = 1, 1, 1`); restore the commented line for the full
10 g–2.5 kg sweep.

## 7. Calibration cache mechanics

Estimators with `requires_calibration=True` need an **empty-gripper baseline at the weigh
pose** (`tau_ss_empty` for pid_error, `q_empty`/`z_empty` for lyapunov, `r_empty` for
momentum_observer). In the FSM pipeline, `InitState`:

1. Checks `configs/calibration.yaml`; if its stored `weigh_qpos_used` matches the active
   weigh pose within 1e-4 rad, loads the cached keys (running calibration only if this
   estimator's keys are missing).
2. Otherwise runs an in-sim calibration hold (move → enter estimator mode → settle →
   hold) and merges the new keys into the YAML.

The cache is shared across estimators (keys merged), invalidated by changing
`weigh_qpos`, and deletable with `verify_estimators.py --clear-cache`. The baseline is
genuinely nonzero — e.g. `r_empty ≈ −1.94 N·m` at wrist_1 — because the Robotiq gripper's
spring-loaded linkage and equality constraints exert steady torques that are not part of
`qfrc_bias`. **The baselines are only valid at the pose where they were captured**; that
matters for motion-phase weighing (see the momentum plan doc).

The tracking pipeline runs the same protocol in-memory each run instead of using the YAML.

## 9. Extending the system

**New estimator**: copy the shape of `estimators/inverse_dynamics.py` — subclass
`Estimator`, implement `reset/update/estimate`, `register("name", Cls)` at module bottom,
add a YAML block under `estimator:` if you have tunables, and import the module in the
entry scripts (`mission.py` and/or `mission_tracking.py`) so registration runs. If you
need an empty-arm baseline, set `requires_calibration=True` and implement the four
calibration hooks; both pipelines will drive them for you.

**New tracking controller**: subclass `TrackingControllerBase`, implement
`command(reference, *, gravity_mask, payload_mass) -> ControlOutput`, and add a branch in
`mission_tracking.make_controller` + gains in `profiles.py`.

**New trajectory stage semantics**: add a flag to `TrajectorySample`/`TrajectorySegment`
and have `run_tracking_mission` act on it — this is the intended mechanism for things
like "collect estimator samples during this motion" (`collect_mass_samples`) and
"feed forward the estimated payload" (`compensate_payload`).
